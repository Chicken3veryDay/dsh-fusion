# @deepseek-ai/dsh-experimental-ticket

English | [中文](README.zh.md)

## Summary

Ticket is the durable coordination record for one piece of work shared by a soft coordinator and direct workers. The Host service stores complete Ticket snapshots in the Session event log and rebuilds them synchronously through `ctx.sessionProjections`. Assignments, execution-slot declarations, work scopes, reports, questions, attention items, coordinator handoff, compare-and-set revisions, and terminal outcomes belong to this domain.

## Use this package

Mount `@deepseek-ai/dsh-experimental-ticket` beside durable Session storage and `@deepseek-ai/dsh-session-projection`. The package registers `ctx.tickets` and the `ticket` Session projection. The Session owns durable state; every public mutation requires an exact registered Agent under `ctx.agents.withInitiator`, matching `actorId` when supplied. Creation requires the technical owner; that owner may also reclaim coordination through `handoff`. Creation and handoff require a registered live coordinator Agent. Missing, stale, or impersonated callers return `TICKET_AUTHORITY`.

The service exposes `create`, `assign`, `claim`, `release`, `report`, `ask`, `answer`, `closeQuestion`, `attention`, `acknowledgeAttention`, `resolveAttention`, `block`, `handoff`, `complete`, `fail`, and `cancel`. Mutating commands carry `expectedRevision`; a stale value returns `TICKET_STALE_REVISION` and leaves the newer state untouched. Workers are direct Session identities supplied by the execution adapter. The current coordinator answers open questions and acknowledges or resolves attention; question authors may also close their own open or answered questions. Acknowledgement retains the blocker. Worker progress, claims, and release preserve unresolved questions and attention; resolving the last blocker recomputes readiness from assignments. Finished or released assignments reject reports; a successful execution settlement leaves its assignment open for the result report. A specification edit reopens completed contributions without attempt history for a fresh model report, retaining old reports as history. Assignments with attempts require a fresh host-admitted attempt; legacy claim cannot reopen them. Exclusive write assignments require a workspace-bearing attempt instead of a legacy claim. Candidate submissions naming assignments without current result reports return `TICKET_ACCEPTANCE` with the assignment identity. Required children constrain acceptance; unfinished, failed, or cancelled children do not prevent parent cancellation or failure. Once every attempt is settled, the coordinator can fail or cancel a Ticket from any nonterminal status, including `ready` after a failed attempt released its assignment.

Mount `TicketTools` when model callers should coordinate through `ticket_*` commands. Mount `TicketExecutionService` with Jobs and Worktree providers when an assignment needs a shared workspace, an isolated worktree, or owned background jobs. The execution adapter admits the durable attempt, checks the direct worker identity, and receives an attempt-bound recorder that serializes execution facts with all Ticket commands without caller CAS. Preparation must match any current initiating Agent. The recorder survives coordinator handoff and preparing Agent disposal. It preserves runtime identity and appends each job id to its receipt before starting the producer. The `prepare` signal cancels only preparation and is not retained once the handle is published; a `startJob` signal stays attached to its Job until that producer settles or the handle is cleaned up. Failed Jobs dominate cancelled Jobs, and either prevents success. Disposal requests cancellation before durable writes and awaits retained producer promises even after Agent cleanup removes their Job records. A Job producer is settled only by its own `done`; a cancellation request that throws fails the stop and is retried by the next disposal. A natural settlement of an activation also waits for its `dispose()` to confirm resource release, because its result may arrive first. A pending or timed-out natural settlement can escalate to disposal. `settlementTimeoutMs` bounds each whole `settle()` or `dispose()` call, including a pending Job admission, the uncertainty record, and the wait for the settlement ledger's durable write; a failed or expired stop rejects with `TICKET_ATTEMPT_STATE` whose `cause` names the failure. When the producer outcome is known but the ledger's write is not durable at the deadline, the call rejects with the retryable `TICKET_SETTLEMENT_PENDING`: the outcome stands, the ledger keeps writing it, and a later `settle()` or `dispose()` repeats the request once storage recovers; a repeated request on a handed attempt has the same deadline. Cancellation or shutdown before any producer starts settles the attempt as cancelled, retaining any known workspace receipt. A failed Worktree creation remains unknown because a checkout may exist. A Subagent start rejected with `ACTIVATION_TEARDOWN_FAILED` failed to roll back a child that may still run, so it also remains unknown; any other rejected start established no child, so that attempt settles. Automatic owner-disposal callbacks do not retry a failed stop; explicit disposal and teardown retry it with a fresh cancellation request. Once the producer outcome is known, Ticket owns the settlement until it is durable, as [the attempt state machine](#attempt-state-machine) describes; disposal of a handle whose root Session is closed rejects with the retryable `TICKET_SETTLEMENT_PENDING`, and resuming that root writes the settlement. Disposal of the caller, worker or root during any preparation phase, including the admission flush, publishes no handle, ends the attempt as cancelled, and rejects `prepare` with `TICKET_AUTHORITY`, inside an `AggregateError` when the deadline of a stopped preparation passes first. When the admission's own flush fails, an identical `prepare` retry repeats the flush and continues preparation; if no retry comes, that disposal or teardown ends the attempt as cancelled. Repeating a settled preparation returns `TICKET_ATTEMPT_STATE`.

A package that owns coordination for a Session registers with `registerCoordinatorAuthority(authority)`, which returns the disposer. `create` asks each authority inside the Session's command queue, in the same synchronous step that reads the Session state and appends the Ticket. The authority receives the requested coordinator (`CreateTicketRequest.coordinatorId`, or the Session id when absent) and may return a replacement; the first replacement wins, so a Ticket created while coordination moves names the coordinator the authority decided at the append. An authority that throws a `TicketError` fails the creation with that error unchanged, such as a retryable `TICKET_COORDINATOR_UNAVAILABLE` from an authority that is still loading; any other exception returns `TICKET_RECOVERY_FAILED` with the original cause. Neither appends anything. A coordinator that is not a registered live Agent returns `TICKET_AUTHORITY` naming it, whether the authority selected it, and the remedy: resume that Agent, or hand coordination back to the Session owner.

A package that owns who may receive work registers with `registerAssignmentAuthority(authority)`, which returns the disposer. `assign` asks each authority inside the Session's command queue, after the actor, CAS, limit and subject checks and immediately before the append, so the decision reflects the assignee at the moment the assignment commits, not when the call was made. The authority receives the Session and the requested `ownerId` and refuses by throwing a `TicketError`, which fails the assignment unchanged and appends nothing; any other exception returns `TICKET_RECOVERY_FAILED` with the original cause. A Session with no registered authority accepts any assignee. The assignment authority is the `assign` case of the command authority below.

A package that owns who may act in a Session registers with `registerCommandAuthority(authority)`, which returns the disposer. Every mutating method asks each authority inside the Session's command queue, after the command's own actor, role and CAS checks and immediately before the append, with the Session, the actor id (the creating initiator for `create`) and a `TicketCommand`. Its `kind` is one `TicketCommandKind`: `create`, `assign` (which also carries `assigneeId`), `claim`, `release`, `report`, `ask`, `answer`, `close-question`, `attention`, `acknowledge`, `resolve`, `block`, `handoff`, `end` (for `complete`, `fail` and `cancel`), `revise`, `submit-candidate`, `check-candidate`, `plan-mission`, `begin-attempt`, `update-attempt` or `settle-attempt`. A refusal is a thrown `TicketError`, returned unchanged with nothing appended; any other exception returns `TICKET_RECOVERY_FAILED` with the original cause. Attempt writes by the execution owner for settlement and recovery are not consulted. A Session with no registered authority accepts every command.

Each queued command is decided by the coordinator and command authorities registered when it was admitted to the queue, plus any registered before it commits. A disposer therefore stops an authority only for commands admitted after it runs. `whenIdle(session)` resolves once every command admitted for that Session before the call has committed or failed; an authority owner that unloads withdraws its registrations, then awaits `whenIdle` for its Sessions before releasing the state its authority reads.

The [Session projection](../../session/session-projection/README.md) is the browser-safe read path. Every `ticket/state` event carries the complete post-change value, so opening a Session or replaying its events produces the same state and rejects malformed or out-of-order revisions. Legacy v1 reports are projected onto the synthesized initial specification so retained results can enter a v2 candidate without rewriting old events. Command admission and replay share semantic validation; invalid commands append nothing. A proposed Ticket cannot complete directly. Persistence flush failures may occur after append and require reading the current revision before retrying. Idempotent attempt-operation retries flush the Session again before reporting success, including retries of an operation that settlement compacted into its attempt's tombstone. The tombstone keeps each retired operation's fingerprint, so a compacted retry with changed arguments returns `TICKET_OPERATION_CONFLICT`, and reusing such an id for another attempt returns `TICKET_ATTEMPT_STATE`.

Work scopes normalize slash-separated relative paths, collapse `.` and `..`, and reject workspace escapes, absolute paths, drive prefixes, and backslashes. An assignment scope must stay within a declared Ticket scope without escalating read access to write access; a Ticket with no declared scopes leaves assignment declarations unrestricted. Attempt admission atomically excludes overlapping write scopes when either declaration is exclusive in the same shared execution world. Scope checks and append run synchronously; unrelated roots do not wait for another root’s flush. Reservations survive root Session closure and remain held through stopping, unknown status, or failed settlement flushes. Activation reads no stored log. The first shared-workspace admission lists storage and folds only the `ticket/state` events of each stored root that is not live, without resuming producers; later admissions reuse that scan. A listing failure, or a stored root that cannot be read, refuses shared-workspace admission with `TICKET_RECOVERY_FAILED` naming the cause or root, and the next admission retries it. When a root's stored Session no longer exists, its reservations are released unless an owner in this host still awaits its producer's outcome; deleting a log does not settle a producer, so that owner's reservation is released once it hands an outcome to the ledger. A live root that fails replay is reported against that root and retains its known scopes; unrelated scopes remain available. Isolated worktrees and distinct execution worlds remain independent; scopes do not confine filesystem access. Each attempt that `TicketExecutionService` admits also registers a reservation on the root context when the admission is recorded, and every admission in any Ticket service generation collects the shared-workspace ones through the `ticket/collect-reservations` event. Such a reservation leaves when the attempt is handed to the settlement ledger or released, when its root Session log records the attempt settled, or, once the attempt is `unknown`, when its producers' own signals prove they stopped, including after the execution service that admitted it was torn down. A replaced service therefore excludes a producer that is still writing even when its root log was deleted and its Job record was removed.

## Understand the implementation

The package has three small layers:

- [`src/types.ts`](src/types.ts) owns branded ids, JSON-compatible snapshots, requests, browser projection types, and the durable event declaration.
- [`src/projection.ts`](src/projection.ts) validates and folds `ticket/state` events synchronously. It rejects revision gaps, immutable identity changes, duplicate nested ids, and illegal lifecycle transitions.
- [`src/index.ts`](src/index.ts) serializes commands per Session, enforces authority and bounds, appends whole snapshots, checkpoints through `ctx.sessions`, and exposes the `ctx.tickets` service seam.

<a id="attempt-state-machine"></a>
### Attempt state machine

[`src/attempt-lifecycle.ts`](src/attempt-lifecycle.ts) is the specification. `TicketExecutionService` passes every event of an execution-owned attempt through `transitionAttempt`, the only writer of its phase, and runs the entry actions of the new phase. The tables below are rendered from that function; a test fails when they differ.

Phases: `admitting` holds the execution reservation until `beginAttempt` appends the admission. `unflushed` is an admission in the in-memory log whose flush failed. `preparing` begins when the admission is appended, flushes it, and records the workspace receipt and, for in-process attempts, the runtime receipt; no producer exists, nothing after the admission starts before it is durable, and only a Ticket write can be in flight, so an abort here hands the attempt over as cancelled at once. `worktree` and `activating` wait for a Worktree or Subagent provider. `launched` holds an established dedicated-process or remote activation and records its runtime receipt before publication; an abort during this write waits for publication and activation stop before handing over. `running` is a published handle. `stopping` observes every producer; `natural` and `cancel` name the sticky cancellation intent. `unknown` is a stop that did not establish producer settlement. In both, `captured` is the outcome the producers reported before their resource release failed; it is final and takes precedence over a later cancel intent. `uncertain` is a provider failure after which a Worktree checkout or a Subagent child may remain. `handed` means the settlement ledger holds the outcome. `released` means no attempt was admitted.

Events: `caller-abort` is the `prepare` signal, attached only until that preparation publishes or rejects. `owner-disposed` is disposal of the caller, the technical root, and before publication the assignment owner or afterwards the in-process worker. `teardown` is service disposal or replacement. `admitted`, `admission-unflushed` and `admission-refused` are the three results of `beginAttempt`. `retry` is an identical `prepare`. `effect-established`, `effect-refused` and `effect-failed` end the provider call of `worktree` or `activating`: `effect-refused` is a Subagent rejection that certifies no child remains, and `effect-failed` is any Worktree rejection or a Subagent `ACTIVATION_TEARDOWN_FAILED`. `stage-failed` is a failed receipt write, identity check or Ticket read. `settle` and `dispose` are the handle methods. `producers-settled` means every producer reported its result and its resource release; the cell shows a succeeded report, and a `cancel` intent turns any outcome other than `failed` into `cancelled`. `cleanup-failed` means every result is known but a release was not confirmed within the deadline or was rejected. `stop-failed` is a settlement timeout before every result is known, a cancellation request that throws, or a rejected activation result. `cancel-failed` is a cancellation request that throws, including one sent by a `startJob` signal: inside a stop, that stop then applies `stop-failed` or `cleanup-failed`; outside a stop, the producer keeps its reservation until its own settlement signal arrives, and the failure is logged with the attempt. `reconciled` is a different `prepare` that finds the attempt settled by a host caller.

Cells: `—` keeps the phase, `✗` rejects with `TICKET_ATTEMPT_STATE`, and `aborted:`, `natural:`, `cancel:` or `captured:` name the variant of the current phase a result applies to; the `captured` variant is shown with a `succeeded` capture.

Entry actions: becoming aborted aborts the preparation lifetime that every provider call observes. Entering `stopping` starts one stop. Each entry to the `cancel` intent sends a fresh cancellation request to every producer that has not finished, so `dispose()` after a failed request asks again, and a producer that has already finished is observed without one. One `settlementTimeoutMs` deadline bounds the whole stop: joining a pending Job admission, observing the producers, writing the uncertainty record, and waiting for the ledger to make a handed outcome durable. A ledger write still pending at that deadline rejects the call with `TICKET_SETTLEMENT_PENDING`; it does not apply `stop-failed`, because `handed` is terminal. A failed or expired observation applies `stop-failed` or `cleanup-failed` before any write, then writes `stop-unknown` or `cleanup-unknown` once; a write still pending at the deadline continues, and its failure is logged. Entering `handed` gives the outcome and any known workspace receipt to the ledger synchronously, before any write that can fail; entering `handed` or `released` drops the execution reservation and the reservation registered on the root context. Aborting a preparation through its `prepare` signal, owner disposal or teardown ends the caller's wait within one `settlementTimeoutMs` deadline, which a preparation failure also starts; no running handle survives an abort. The attempt continues after its caller stops waiting: the write or provider call in flight completes, and the attempt reaches `handed`, `unknown` or `uncertain`, holding its reservation until the write that records that state is durable. An abort in `preparing` queues the cancelled settlement behind the write in flight. When the attempt finishes first, a successful ledger write leaves only the preparation failure, and a failed ledger or uncertainty write is reported with it. At the deadline, `prepare` rejects with an `AggregateError` of the preparation failure and a `TICKET_SETTLEMENT_PENDING` naming the step still running; that step needs no retry, and its late failure is logged.

The settlement ledger in `TicketService` writes the `settled` snapshot to the live root. A closed root returns `TICKET_SETTLEMENT_PENDING`; resuming it replays the write. A failed flush is repeated by the next settlement retry or Ticket write on that root, and teardown makes one last attempt. Execution teardown waits for its attempts, including their handed writes, until one `settlementTimeoutMs` deadline from its start, then rejects with `TICKET_SETTLEMENT_PENDING` while the ledger keeps those writes. If the root's stored Session is deleted, the outcome is discarded with it. The scope reservation and ledger entry are released only by the flush that makes the settlement durable, or by deletion of the root's stored Session once the ledger holds the outcome. `failed` and `cancelled` release the assignment; `succeeded` leaves it open for its result report. A durable `unknown` attempt is settled by a host caller with `settleAttempt`.

The lifecycle consumes only signals each producer guarantees. Registry records, terminal record status and Agent disposal prove nothing about a producer and are never read as settlement.

A replacement waits rather than adopts. A new Ticket or execution service never takes over a run of an earlier generation; it only excludes that run's scopes through the reservation registered on the root context until the producers' own signals prove they stopped or a host settles the attempt. Every admitted attempt registers such a reservation, whatever its workspace, so a root closed during replacement and resumed afterwards leaves an attempt with a live producer unsettled instead of recovering it as `cancelled`.

After a restart, a resumed root settles an attempt as `cancelled` when its reserved execution operations show that this host family admitted it, no owner in this host holds it, meaning neither this Ticket service's ledger nor a reservation registered on the root context by any execution service generation, and it either ran in process and is `preparing`, `running` or `stopping`, or is still `preparing` in any placement, because no producer starts before the workspace stage. Roots live when Ticket activates are left to their earlier owner. Manual attempts, and dedicated-process or remote attempts past their workspace stage, stay reserved until a host caller settles them.

The Ticket service is independent of Fusion, Agent Teams, Worktree, Jobs, UI, polling, and generic subagent spawning. The optional execution adapter composes existing Jobs, Worktree, and Subagent providers while Ticket retains durable assignment and handoff semantics.

<a id="model-experience"></a>
## Model Experience

### Host coordination and optional tools

#### What the model sees

The core service and `ticket/state` event stay outside model context. `TicketTools` is opt-in and registers direct-worker commands that return JSON Ticket views; it does not create workers or bypass the CAS revision check. Specification revision, candidate submission, and criterion checks use `ticket_revise`, `ticket_submit_candidate`, and `ticket_check_candidate`; attempts stay host-owned, and `ticket_report` takes the active `attempt_id`. Creation is restricted to the caller’s Session and coordinator identity; use handoff to transfer coordination. Cross-Session reads expose only Tickets where the caller coordinates or owns an assignment. There is no automatic event trigger.

#### Token effect

Ticket events are log-only and add no model tokens by themselves.

#### KV Cache effect

Ticket state changes do not alter request headers or model prompt prefixes.

## Known Limitations and Deferred Work

- The execution adapter owns Jobs and Worktree lifetimes in memory; the Ticket log retains the assignment and slot state, while provider-specific job and checkout recovery remains provider-owned.
- The package has no source admission policy or browser supervision UI. Consumers decide which Ticket commands and execution modes require human approval.
- Ticket snapshots reserve byte capacity for uncertainty, minimal settlement records, and a minimal Ticket cancellation summary before admitting more state. Attempt count uses `maxReports`; operations are bounded by snapshot bytes rather than report count. The `ticket-execution:` operation-id prefix is reserved for admitted execution facts. Operation fingerprints use SHA-256; retained JSON fingerprints remain readable. Settled attempts compact tagged operation records into one settlement record retaining retired ids and fingerprints; replay preserves those refusals, while settlement retries retain their fingerprint and durability check. Settlement records written before fingerprints were retained keep only ids, so a retry of one of their operations for the same attempt is acknowledged whatever its arguments. Historical untagged operations, reports, questions, and attention are not compacted.
- A damaged root with no recoverable Ticket placement cannot reserve an identifiable workspace; its recovery warning requires repair before resuming that root. Known reservations remain held. A closed root must be resumed before a settlement can be persisted; the outcome is held in memory until then, so an in-process attempt whose host exits first is recovered as `cancelled` and other placements stay reserved.
- A reservation registered on the root context whose producers cannot confirm release, such as an activation whose cleanup failed or a Subagent start whose rollback failed, is released only when a host settles its attempt. The Subagent manager retries releasing a rejected start's execution on drains and parent disposal, but that rejection returns no activation, so Ticket cannot observe the retry. If its root Session log was deleted, no host can settle it, so it holds until the host exits.
- An attempt whose uncertainty record could not be written because its root was closed keeps its last durable status, such as `running`, while a producer of an earlier service generation in this host still runs; no later generation rewrites it. A resume of that root leaves the attempt to the producer, and the first resume after the producer's own signals release the reservation recovers it as `cancelled` unless a host settled it first.
- The activation manager memoizes a failed release, so a later `dispose()` of that activation returns the same rejection instead of retrying the release; the attempt stays `unknown` until a host settles it with `settleAttempt`.
- The first shared-workspace admission after activation reads every stored root log once; cost grows with stored history until a compact reservation index exists.
- A service that injects `tickets` unloads when `ctx.tickets` reloads. In the [Workstream profile](../workstream-profile/README.md#known-limitations-and-deferred-work), that unloads `workstreams`, whose shutdown drains every member and aborts each running member turn.
- A Ticket is rooted in one Session log. Cross-Session replication and source-specific ingress remain adapter responsibilities.
